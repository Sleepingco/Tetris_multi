# 고정 유예와 무한 버티기 방지 수정안

- 분류: 게임 규칙·입력 제한
- 작성일: 2026-10-19
- 조사 기준: `main`, `b0f6f0a`
- 상태: 공용 규칙과 싱글·멀티 연결 구현 완료. 검증 결과는 9절에 기록한다. 커밋·배포 전.
- 목적: 정상적인 착지 후 조작 시간을 보장하면서, 벽차기와 재낙하로 같은 조각을 계속 유지하는 경로를 막는다.
- 500ms와 15회는 이 프로젝트에 적용한 초기 정책값이다. 모든 상용 작품의 현행 규칙과 완전히 같다는 의미는 아니다.

## 1. 수정 전 코드가 방지하던 것

| 방어 | 현재 동작 | 한계 |
| --- | --- | --- |
| 고정 유예 | 첫 자동 하강 실패에서 대기하고, 같은 조각의 다음 하강 실패에서 고정 | 실제 하강 성공 시 대기 기록을 지워 같은 높이에서 반복 복구 가능 |
| 일반 이동·회전 | 성공해도 중력 누적 시간과 기존 고정 대기 기록을 초기화하지 않음 | 벽차기로 위로 이동한 뒤 하강하는 경로는 별개 |
| 키보드 자동 반복 | 회전·홀드·하드드롭의 `event.repeat` 무시 | 키를 다시 누르는 정상 입력까지 차단하지 않음 |
| 홀드 | 고정 전 한 번만 허용 | 고정 제한 자체를 대신하지 않음 |
| 클라이언트 입력 | 같은 tick·조각에 최대 4개 등록, 정상 tick에서 최대 4개 소비 | 조각별 조작 횟수·누적 대기시간의 상한이 아님 |
| 서버 입력 | 기본 초당 60개, 소켓별 미처리 입력 최대 120개 | 낮은 빈도로 반복하는 벽차기도 가능 |
| 서버 신뢰 경계 | 세션·방 권한, payload, sequence·pieceIndex, 서버 충돌·이동 판정 검사 | 허용된 게임 동작을 이용한 버티기는 해결하지 않음 |

조사 기준 코드의 기본 중력 주기는 500ms였다. 고정 유예는 착지 순간부터 세는 별도 타이머가 아니라 **자동 하강 실패 두 번**에 연결돼 있었다. 바닥에 닿은 정확한 시점부터 항상 500ms 뒤에 고정되는 구조가 아니었다. 소프트드롭 실패는 별도 경로에서 즉시 고정하고 하드드롭도 즉시 고정했다. 아래 1~3절은 수정 전 조사 기록이며, 적용된 정책은 4절과 9절을 따른다.

관련 코드:

- [클라이언트 실행](../../src/client/game/runtime/tetris.ts): `processTick`, `applyMoveIntent`, `startGravity`, `holdPiece`.
- [서버 실행](../../src/server/services/playerGameplayStep.ts): `applyAuthoritativeGravityStep`, `applySoftDrop`, `applyHardDropInput`.
- [서버 실행 주기](../../src/server/services/authoritativeTickerService.ts): 기존 `groundedPieceIndex`는 제거했으며 `resetPlayerGravity`, `processDuePlayer`는 유지한다.
- [키 반복 차단](../../src/client/game/runtime/input.ts), [입력 빈도 제한](../../src/server/services/socketRateLimitService.ts), [입력 큐·권한 검사](../../src/server/sockets/multiplayerHandlers.ts).

## 2. 싱글과 멀티의 공유 범위

| 경로 | 규칙 계산 | 실행과 최종 상태 |
| --- | --- | --- |
| 싱글 | 공용 `core` | 브라우저 `runtime/tetris.ts` |
| 멀티 내 보드 | 공용 `core` | 같은 브라우저 런타임으로 예측, 서버 결과로 보정 |
| 멀티 최종 판정 | 같은 공용 `core`를 서버에서 import | `playerGameplayStep.ts`와 서버 ticker |
| 멀티 상대 보드 | 서버 snapshot 결과 표시 | 독립적인 로컬 판정·중력 실행 없음 |

[싱글 진입점](../../src/client/pages/tetrisSingle.tsx), [멀티 세션](../../src/client/game/entry/multiplayerGameSession.ts), [서버 core 로더](../../src/server/services/gameCoreLoader.ts)를 기준으로 확인했다. 수정 전에는 공용 충돌·벽차기가 있어도 고정 시점의 정책은 두 실행 계층에 나뉘어 있었다. 수정 후에는 고정 예산 계산도 공용 core를 사용하며, 시계와 실행 순서는 각 실행 계층이 담당한다.

## 3. 재현한 빈틈과 원인

1. 빈 보드 바닥에 가로 I 조각을 놓고 첫 하강 실패로 유예를 만든다.
2. 시계·반시계 회전을 조합해 바닥 벽차기로 위로 올라간 뒤 가로 상태로 되돌린다.
3. 자동 하강을 두 번 진행해 같은 깊이로 돌아온다. 하강 성공 때문에 기존 유예 기록은 해제된다.
4. 다음 하강 실패에서 다시 첫 유예를 받는다.
5. 회전 방향을 번갈아 조합하면 위치·방향도 원래 상태로 돌아와 같은 동작을 반복할 수 있다.

| 가상 시간 재현 | 서버 ticker | 싱글 런타임 | 멀티용 예측 런타임 |
| --- | --- | --- | --- |
| 바닥 O 조각 회전, 1초 진행 | 다음 조각으로 전환 | 동일 | 동일 |
| I 조각 위 순환, 60.5초·회전 80회 | 같은 조각, 고정 0회 | 동일 | 동일 |

핵심 원인은 **이미 도달했던 깊이로 다시 내려오는 것과, 처음으로 더 아래까지 진행하는 것을 구분하지 않고 유예를 새로 주는 것**이었다. 당시에는 조각별 리셋 횟수와 시간 한도도 없었다.

앞선 조사에서 관련 기존 테스트 212개가 통과했고, 위 두 조건은 임시 CommonJS 검사로 재현했다. 임시 검사는 저장소의 정식 회귀 테스트가 아니며 실제 브라우저 간 대전 검증도 아니다. 이번 문서 작성 후 테스트를 재실행한 결과로 기록하지 않는다.

## 4. 적용한 고정 정책

| 항목 | 적용 규칙 |
| --- | --- |
| 최초 착지 | 아래 한 칸을 배치할 수 없어진 시점부터 고정 시간 500ms 시작 |
| 성공한 좌우 이동·회전 | 최초 착지 이후 최대 15회까지 고정 시간을 500ms로 갱신하고 횟수 증가 |
| 실패한 입력 | 시간 갱신·횟수 증가 없음 |
| 리셋 상한 이후 | 이동·회전은 허용하되 같은 깊이에서 시간을 더 갱신하지 않음 |
| 위로 벽차기·공중 복귀 | 높이 상승 자체로 한도를 복구하지 않음. 성공한 회전·이동이면 남은 15회 한도에서 시간 갱신·횟수 증가. 최초 착지 후 시간은 공중에서도 감소 |
| 기존 깊이로 재낙하 | 남은 시간과 횟수 복구 없음 |
| 처음으로 더 아래 진행 | 최저 도달 row를 갱신하고 시간 500ms·횟수 0회로 갱신 |
| 시간 만료 | 접지 중이면 고정. 공중이면 만료 상태를 유지하고 다음 접지 시 고정 |
| 소프트드롭 | 막혔다는 이유만으로 즉시 고정하지 않고 같은 착지 정책 적용 |
| 하드드롭 | 남은 시간·횟수와 무관하게 기존처럼 즉시 고정 |
| 정상 spawn·허용된 hold 교체 | 새로 활성화한 조각의 고정 상태 초기화. 기존 hold 1회 제한 유지 |

15회는 입력 금지 횟수가 아니라 **고정 시간을 갱신할 수 있는 횟수**다. 15번째 갱신은 허용하고 16번째부터 추가 갱신을 하지 않는다. 총 생존시간이 항상 500ms라는 뜻도 아니다.

`lowestRow`는 SRS 기준 좌표인 `activePiece.row`의 지금까지 가장 큰 값으로 정한다. 회전마다 달라지는 조각 최하단 cell의 좌표로 판정하지 않는다. 이전 최대 row와 같은 위치로 돌아오는 것은 새 하강으로 인정하지 않는다. 실제 깊이 진행은 유한한 보드 안에서만 가능하므로 같은 높이의 순환 회전으로 한도를 계속 회복할 수 없다.

만료 확인은 중력 주기뿐 아니라 **입력을 적용하기 전·후에도** 한다. 만료된 접지 상태에서 새 회전으로 먼저 도망가거나 중력 검사 사이에 접지·이탈을 반복하는 우회를 막는다. 공중의 조각은 강제로 고정하지 않는다.

동시에 조건이 생기면 경과 시간 반영과 기존 접지 상태의 만료 검사를 먼저 한다. 이후 허용된 입력을 적용하고, 새 최저 row 갱신을 일반 이동·회전의 갱신보다 우선한다. 한 동작에 두 번 리셋 횟수를 반영하지 않는다. 최초 접지 처리 뒤 결과 상태의 만료도 검사한다.

## 5. 구현 경계와 필요한 상태

공용 [core/lockDelay.ts](../../src/client/game/core/lockDelay.ts)에 고정 유예를 계산하는 순수 함수를 둔다. 이전 유예 상태, 현재 기준 row, 경과 시간, 성공한 이동·회전의 갱신 여부와 접지 여부로 다음 유예 상태를 계산하고 고정 필요 여부를 판단한다. DOM·timer handle·Socket·점수는 넣지 않는다. 접지는 기존 `canPlacePiece`로 한 칸 아래를 검사해 계산한다.

| 상태 | 의미 |
| --- | --- |
| `hasTouchedGround` | 현재 활성 조각이 처음 접지한 적 있는지 |
| `remainingMs` | 남은 고정 시간. 0이면 만료이며 별도 `expired` 상태를 중복 저장하지 않음 |
| `resetCount` | 현재 깊이에서 사용한 갱신 횟수, 0~15 |
| `lowestRow` | 현재 활성 조각의 최저 도달 기준 row |

이 값은 싱글의 게임 상태와 멀티 서버의 authoritative player state가 각각 자기 게임의 원천으로 소유한다. 멀티 클라이언트는 서버 상태의 복원·미확정 입력 예측을 위한 복사본만 가진다. 남은 시간은 직렬화 가능한 gameplay 예산이고 실제 timer handle은 실행 계층에 둔다.

기존 `automaticGroundedPieceIndex`·`groundedPieceIndex`의 유예 역할은 새 정책으로 교체하고 수정 가능한 별도 원천으로 남기지 않는다. 중력 누적값과 stale callback 차단용 generation은 유지한다.

필수 연결 경계:

- 클라이언트 16ms tick, 서버 100ms ticker에서 고정 시간을 갱신한다. 중력의 500ms 주기와 분리하고 정상 스케줄링 조건의 임계값 오차는 각 실행 tick 이내로 검증한다. 늦은 callback은 실행 계층의 단조 증가 시계로 실제 경과 시간을 반영한다.
- 중력 재시작과 유예 초기화를 분리한다. 일반 입력·snapshot 적용이 시간을 새로 주면 안 된다.
- countdown·줄 삭제 연출·종료 상태에는 새 조각의 유예 시간을 소모하지 않는다. 서버는 서버 시간만 사용하며 client `tick`이나 요청으로 한도를 연장하지 않는다.
- 입력과 timer 갱신은 같은 마지막 갱신 시점을 기준으로 시간을 한 번만 반영한다. 여러 입력을 한 번에 처리해도 중복 차감하지 않는다. 입력 중 조각이 고정되면 이전 조각용 나머지 입력은 다음 조각에 적용하지 않는다.
- snapshot에 유예 상태를 포함하고 clone·DTO·schema·복원을 함께 갱신한다. 같은 조각의 보정·재접속에서 서버 예산을 복원하며 늦은 snapshot·입력 재실행으로 근거 없이 예산을 되돌리지 않는다. 서버가 인정한 정상 리셋은 복원한다. 서로 다른 기기의 절대 시각을 비교하지 않는다.
- hold는 현재 `pieceIndex`를 바꾸지 않을 수 있으므로 교체 경로에서 명시적으로 초기화한다. `pieceIndex`만으로 새 활성 조각을 판단하지 않는다.
- PVE AI도 같은 서버 고정 정책을 적용한다. 별도 AI 행동 주기에도 시간 진행을 연결하고 도중 고정된 조각의 오래된 계획은 기존 조각 번호 검사로 폐기한다. AI 평가식·학습 모델은 변경하지 않는다.

## 7. 검증·완료 기준

| 검사 | 통과 기준 |
| --- | --- |
| 기본 착지 | 무입력 시 500ms 전 고정 없음, 만료 후 실행 tick 이내 한 번만 고정 |
| 성공·실패 입력 | 성공한 이동·회전만 갱신, 실패·키 자동 반복으로 시간 복구 없음 |

| 경계 시간·입력 순서 | 같은 tick 만료/입력 우선순위, 중복 시간 차감·오래된 조각 입력·중복 placement 없음 |
| 동기화 | correction·재join·응답 단절 복구 뒤 근거 없는 예산 증가 없음, 오래된 snapshot으로 되감기 없음 |
| PVP·PVE | 양쪽 정책 일치, AI 계획 중 고정·다음 조각 전환 정상, 줄 삭제·공격·종료 중복 없음 |

구현 후 `bash scripts/verify.sh`를 반드시 실행한다. 추가 검증은 `test/testTetrisRuntime.js`, `test/testAuthoritativeTickerService.js`, `test/testPlayerGameplayStep.js`, `test/testPlayerStateInput.js`, `test/testMultiplayerGameSession.js`, `test/testStateSerialization.js`, `test/testSocketContracts.js`, PVE 관련 테스트와 새 E2E를 포함한다. 브라우저에서는 정상 T스핀 조작·빠른 좌우 이동·드롭·hold, 실제 2탭 대전과 재접속을 확인한다. 가상 시간 결과만으로 실제 대전 확인을 완료 처리하지 않는다.

## 8. 범위·위험과 rollback

- 기존 자동 고정 시점과 막힌 소프트드롭 동작이 바뀐다. 구현 후 조작감을 직접 확인하며 500ms·15회 조정은 공통 설정으로 한다.
- 전송 지연과 tick 간격 때문에 예측 시점은 서버와 약간 다를 수 있다. 최종 고정은 서버가 결정하고 보정 뒤 중복 줄 삭제·공격·이펙트가 없어야 한다.
- snapshot 필드 추가는 엄격한 schema와 기존 열린 클라이언트에 영향을 준다. 구버전 탭의 처리·새로고침 안내를 확인하고 서버·클라이언트를 같은 릴리스로 맞춘다. 이 문서는 배포 승인이 아니다.
- T스핀 Mini 분류, 회전 이력 버그 수정, 점수·공격표, 디자인·사운드 변경과 새 라이브러리는 제외한다. 새 로그를 과거 데이터와 비교할 때 고정 정책 변경 이력을 구분한다.
- rollback은 서버·클라이언트·snapshot 계약을 함께 이전 코드로 복구한다. 운영 DB row·volume·기존 로그·학습 산출물은 삭제하지 않는다. rollback은 기존 버티기 빈틈도 다시 열 수 있다.

## 9. 구현과 검증 결과 (2026-10-19)

- 싱글·멀티 예측·서버가 같은 `createLockDelay`·`updateLockDelay`·`shouldLockPiece`를 사용한다. 기존 조각 번호 기반 유예 기록을 제거하고 중력과 독립적인 단조 증가 시계로 예산을 진행한다. 입력 전후에도 만료를 확인하며 공중에서는 고정하지 않는다.
- 서버는 클라이언트가 보낸 시각·예산을 사용하지 않는다. snapshot에 유예 상태를 복사해 보내고 보정·재join에서 복원한다. 같은 상태의 중복 snapshot으로 남은 시간을 늘리지 않으며, 오래된 tick의 snapshot은 제외한다. 줄 삭제 연출 동안 다음 조각의 예산은 소모하지 않는다.
- PVE는 기존 AI 입력 경로에서 같은 서버 예산을 적용한다. 계획 도중 조각이 고정된 경우 기존 계획 불일치 처리와 학습 로그 제외 규칙을 유지한다. 점수·공격표·T스핀 분류·모델·데이터셋·운영 DB는 변경하지 않았다.
- 새 core·통합 테스트는 499/500ms, 15/16번째 갱신, 새 최저 row, 공중 만료, 실패 입력, 벽차기 순환, snapshot 복사·복원과 막힌 소프트드롭을 검사한다. 서버 ticker·싱글·멀티 예측의 I 순환이 4초 이내 고정되는 회귀 조건을 추가했다.
- 필수 `bash scripts/verify.sh`는 typecheck·build·artifact와 Node 682 pass·기존 조건부 1 skip·실패 0으로 통과했다. 새 Chromium E2E 3/3에서 싱글 I 벽차기, 실제 2탭 PVP 보드 수렴, PVE 접속 복구 시 예산 보존을 확인했다. 최종 전체 Chromium E2E도 50/50 통과했으며 기존 공격·상쇄·게임 종료·재시작·네트워크 복구 회귀를 포함한다.
- 직접 플레이한 조작감·실기기 프레임·Linux CI·운영 배포는 이번에 확인하지 않았다. snapshot 계약이 바뀌므로 배포 시 서버·클라이언트를 함께 갱신하고 기존 열린 탭은 새로고침해야 한다. rollback은 8절을 따른다. 커밋·push·배포는 수행하지 않았다.
