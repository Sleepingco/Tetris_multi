# 데이터 정제·AI 학습 대화 요약

> 조사 배경 기록. 아래의 "현재"와 다음 순서는 2026-10-12 대화 기준이다.
> 이후 40행/v3 전환과 Human 조작·hold 설계는 [현재 계획](ai-plan.md)을 따른다.
> 이 요약과 연결된 V4 재학습 제안을 완료 실험이나 새 실행 지시로 읽지 않는다.

작성일: 2026-10-12 (Asia/Seoul)

## 현재 목적과 진행 상태

운영 DB에서 가져온 누적 게임 로그를 정제하고, 중복 없이 학습·평가에
사용해 AI 개선을 진행하려 한다. 우선 작업은 데이터 정제다.

상세 계획은 [신규 로그 정제와 V4 재학습 계획](new-log-cleaning-training-plan.md)에
작성되어 있다. 이름의 '신규 로그'는 새로 가져온 파일을 뜻하며, 파일의
모든 게임이 신규 플레이 또는 모델 미학습 게임이라는 뜻은 아니다.

현재까지 수행한 것은 입력 파일의 읽기 전용 분석과 계획 문서 작성이다.
사용자가 정제 시작을 요청해 구현 전 코드·환경 확인을 시작했지만,
요약 요청으로 전환됐다. 정제 스크립트 작성, 정제 결과 생성, 후보 dataset
export, 모델 학습과 운영 적용은 아직 수행하지 않았다.

## 5시간 게임에 대한 확인

불완전 16게임 중 10게임은 기록된 이벤트의 관찰 구간이 10분을 넘는다.
가장 긴 게임은 약 5시간 54분(21,236.542초) 동안 이벤트가 기록됐다.

- 시작 이벤트: 1건
- 종료 이벤트: 0건
- Human placement: 0건
- heuristic AI placement: 20,065건

이 게임은 사람이 5시간 플레이했다는 증거가 아니라, 종료 기록 없이 AI
배치가 계속 저장된 사례다. placement에 남지 않은 키 입력의 존재 여부는
이 로그만으로 판단할 수 없다. 왜 AI 기록이 계속됐는지는 아직 조사하지
않았으며 AFK나 서버 오류로 단정하지 않는다.

## '과거 게임 + 추가분'의 의미

사용자는 이번 파일이 기존 게임에 추가 기록이 붙은 누적 데이터라고 설명했다.
프로젝트 표준 DB export는 날짜 필터 없이 전체 테이블을 내보내므로,
그 명령으로 생성한 파일은 누적 스냅샷으로 취급하는 것이 맞다.
이전 답변에서 파일 전체를 신규 게임 묶음처럼 표현한 부분은 바로잡았다.

다만 DB에 과거부터 있던 게임과 AI가 이미 학습한 게임은 구분해야 한다.
오래된 운영 게임도 모델이 학습하지 않았다면 미학습 게임일 수 있다.

파일 앞 10행을 비교했을 때 현재 로컬 과거 로그와 이번 덤프는 서로 다른
게임이었다. 각 파일의 앞 10행은 한 게임에 속하므로 누적 관계를 증명하는
표본으로 충분하지 않다. 전체 gameId 비교에서도 로컬 과거 로그 148게임과
덤프 246게임의 교집합은 0개였고, `human-behavior-v2`의 13게임도 겹치지 않았다.

이전 운영 DB 덤프와 과거 75/125게임 학습 snapshot은 현재 확인한 폴더에
없어 직접 대조하지 못했다. 따라서 기존 모델의 학습 데이터 포함 여부는
아직 확정하지 않았다. 이번 파일을 이전 덤프와 단순히 이어 붙이지 않고,
이번 누적 스냅샷을 기준으로 처리한다.

## 작성된 정제 계획

사용자가 제시한 핵심 제외 기준은 정상적으로 종료되지 않은 게임과
지나치게 오래 진행된 게임이다. 계획에는 다음 판정을 넣었다.

1. 시작·종료 누락, 중복 lifecycle, 비정상 종료는 게임 전체를 제외한다.
2. 시작·종료 시각이 유효하지 않으면 제외한다.
3. 장시간 게임은 10분을 초기 검토선으로 제안했다. 최종 cutoff는 아직
   확정되지 않았고, 실제 평가·학습 전에 정책으로 고정한다.
4. 정상 종료 게임의 시간은 `occurred_at`으로 계산한다. DB 저장 시각인
   `ingested_at`을 플레이 시간으로 사용하지 않는다.
5. 종료되지 않은 게임에는 실제 duration 대신 관찰 구간만 기록한다.
6. Human 학습에서는 정상 완료 게임의 승자·패자를 모두 포함하고,
   초반 pieceIndex 0~4와 유효하지 않은 placement는 기존 정책대로 제외한다.

정제 시작 요청 직후에는 10분 기준을 적용하고 결과를 보고할 예정이라고
안내했지만, 해당 기준으로 실제 정제를 실행하지는 않았다. 이번 입력의
완결 게임은 모두 10분 미만이므로 이 검토선으로 추가 제외될 완결 게임은 없다.

원본에서 행을 삭제하지 않는다. 제외 사유는 별도 출력에 남기고,
게임 하나의 일부 구간만 잘라서 학습에 넣지 않는다.

## 구현할 처리 경로

원본은 PostgreSQL row 형식(`event_type`, `game_id`, `payload`)이고,
기존 exporter는 앱 이벤트 형식(`eventType`, `gameId` 등)을 기대한다.
payload와 시간 필드까지 계약에 맞게 변환해야 한다.

또한 기존 exporter는 파일 전체를 문자열로 읽는다. 이번 파일은 단일
문자열 크기 한계에 걸릴 수 있어 줄 단위 streaming 처리가 필요하다.
기존 validator, exporter 정책과 candidate builder를 재사용한다.

예정 산출물은 다음과 같다.

- `manifest.json`: 원본 checksum, 정제 정책, 포함·제외 수와 분포
- `game-quality.jsonl`: 게임별 시간·lifecycle·판정 근거
- `rejected.jsonl`: 제외 기록과 사유
- `train.jsonl`, `validation.jsonl`: 학습·평가 후보 데이터

새 출력 경로를 사용하고 기존 snapshot을 덮어쓰지 않는다. 누적 데이터의
중복은 event identity로 확인하며, 같은 ID의 내용이 다르면 충돌로 기록한다.

## 학습에 사용할 전략

1. 정제된 전체 스냅샷을 만든다.
2. 기존 모델이 실제 학습한 gameId 목록과 artifact를 확보한다.
3. 이미 학습한 게임과 미학습 게임을 구분한다.
4. 미학습 게임으로 기존 모델을 먼저 평가한다. 시간상 이후 게임인지
   확인된 경우에만 temporal holdout으로 부른다.
5. 결과 분석 뒤 편입할 게임을 정해 중복 없는 누적 학습 pool을 만든다.
6. 기존 V4 계약으로 다음 모델 후보를 학습한다.
7. 이미 학습에 넣은 게임의 결과를 새 모델의 독립 평가 성능으로 보고하지 않는다.

현재 `human-behavior-v2` manifest는 13게임이며 과거 125게임 기준선의
대체물이 아니다. 과거 학습 snapshot을 확보하지 못하면 별도의 게임 단위
시간 순서 split을 갖는 baseline 실험을 설계해야 한다.

## 이후 AI 개선 제안

현재 V4는 16-feature 선형 Human 선택 모방 모델이다. 기존 기록의 gameplay
평가에서는 500-placement horizon을 휴리스틱 30/30, V4 27/30이 생존했다.
이 결과는 대화 중 새로 실행한 benchmark가 아니라 기존 평가 기록이다.

추천 순서는 다음과 같으며 아직 구현하거나 실험하지 않았다.

1. 깨끗한 데이터로 기존 V4를 재학습해 비교 기준을 만든다.
2. 보드 높이에 따라 구멍의 위험을 달리 볼 수 있게 상황 특징 하나를 실험한다.
   예: `배치 전 높이 × 구멍 변화량`. 배치 전 높이만 더하면 pairwise 차이에서
   사라지므로 상호작용이 필요하다.
3. 실제 게임 실력 개선은 공개된 다음 블록까지 놓아 보는 2단계 탐색을 비교한다.
4. 모델 교체 비교가 필요하면 LightGBM ranker를 후보로 검토한다.
5. 강화학습은 재현 가능한 simulator·평가·보상 기준을 갖춘 뒤 검토한다.

한 실험에 한 변수만 바꾼다. 사람 선택 모방 지표의 개선과 생존·공격·승률의
개선을 별도로 확인한다. 데이터 정제 요청은 이 후속 실험의 자동 실행이나
PVE 기본 AI 교체 승인을 의미하지 않는다.

## 기타 대화와 남은 작업

- TETR.IO 질문에서는 긴 HTML에 화면 구조가 들어가고 실행 코드는 별도
  경로에서 로드될 수 있다고 설명했다. 실제 script 진입점은 확정하지 않았다.
- Umami 직접 추적 수정 커밋으로 `b515669`를 확인했다. 당시 최신 `a71ac05`는
  후보 이미지 준비 변경이었고, 실행 컨테이너의 image ref/ID를 확인하는 명령을
  안내했다. 실제 운영 Docker 상태는 조회하지 못했다.
- PostgreSQL의 `tetris_analytics.game_events`에서 최신 20건을 조회하는 명령을
  안내했다. 대화에서 운영 DB에 연결해 쿼리를 실행하지는 않았다.
- 현재 repository에는 사용자 작업으로 보이는 frontend·보안·테스트·PLAN 변경이
  있다. 요약 작업에서는 이 변경을 수정하거나 stage하지 않는다.

다음 작업은 원본 checksum 재확인, 장시간 정책 고정, streaming 변환·정제
경로 구현과 작은 smoke다. 긴 full 평가·학습은 ML 하네스의 별도 실행 단계로
진행한다. 이 문서 작성은 정제 완료나 모델 성능 개선을 뜻하지 않는다.
