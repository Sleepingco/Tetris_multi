# 하네스 개선 계획

- 작성일: 2026-10-15
- 상태: 1~4단계 적용 및 문서 검증 완료 (2026-10-15)
- 우선 대상: `migration-harness/`의 기록 보관 전환과 `AGENTS.md`의 활성 지침 정리
- 연관 대상: `ai-harness/`의 작업 선택 및 ML 실험 읽기 경로
- 목적: 끝난 마이그레이션의 명세·검증 증거는 보존하고, 현재 개발에 필요한 지침만 활성 상태로 유지한다.

## 1. 유지할 설계와 개선할 문제

사용자가 마이그레이션 작업의 종료를 확인했다. 따라서 migration 실행 절차를 계속 최적화하는 대신 `migration-harness/` 전체를 `docs/archive/migration/`으로 옮겨 당시 계획과 실행 증거로 보관한다. 기존 보류 Goal은 당시 미실행 항목으로 보존하며 현재 할 일이나 완료한 기능으로 바꾸지 않는다.

현재도 유효한 아키텍처·운영·검증 조건은 기존 활성 문서에 남긴다. 과거 명세를 보관하는 것과 현재 계약을 폐기하는 것을 구분한다. 재사용할 구체적인 작업이 없는 범용 migration 실행기는 새로 만들지 않는다.

| 확인한 사실 | 개선 방향 |
| --- | --- |
| 기존 migration 필수 읽기 범위는 루트 지침과 공통 문서를 합해 861줄이다. | 종료된 실행 경로 자체를 활성 지침에서 제거한다. 이 경로의 350~450줄 축소 목표는 폐기한다. |
| migration 폴더에 계획·절차·Goal·실행 기록이 함께 있다. | 내부 구조를 유지해 통째로 보관하고, 완료된 명세를 다시 리팩토링하는 작업은 생략한다. |
| DB blueprint와 production runbook이 migration Goal을 현재 계약·release 기준으로 참조한다. | 현재 운영 기준은 코드·스크립트·활성 운영 문서에 연결하고, Goal 링크는 당시 설계·검증 근거로 구분한다. |
| AI README는 `verify.sh`를 2단계로 설명하지만 실제 스크립트는 5단계다. | 실행 파일을 검증 명령의 원천으로 삼고 문서의 낡은 명령·경로를 수정한다. |
| ML 실험 문서 두 개를 Python 테스트가 직접 읽는다. | 실험 파일 경로와 고정 계약을 유지하고 공통 읽기 지침부터 정리한다. |

## 2. 범위와 보존 조건

이번 개선에 포함한다.

- 루트 지침의 중복 축소와 요청별 읽기 경로 정리
- migration 폴더의 archive 이동과 활성 지침에서의 연결 해제
- 현재 운영 기준과 과거 명세 참조의 분리
- 계속 사용하는 AI 작업 지침과 검증 설명의 일치
- 변경된 문서의 참조 확인과 대표 요청에 대한 지침 검토

이번 개선에서 수행하지 않는다.

- gameplay, 서버·클라이언트 계약, ML 계산·데이터·모델 변경
- 기존 Goal의 자동 재실행, 새로운 기술 마이그레이션 시작
- migration 이외의 실험·실행 기록 이동 또는 삭제
- 종료된 migration workflow·Goal 템플릿의 재설계
- 과거 실행 결과·커밋·checksum의 재작성
- 전체 문서 재배치, Q&A 정리, Git 이력 삭제
- 훅 등록, 사용자 전역 설정 변경, 새로운 범용 실행기 도입

축소 과정에서 반드시 유지할 조건:

- 서버 권위, core의 순수성, React와 Canvas의 상태 소유권
- 사용자 변경 보존과 작업 범위 밖 변경의 사전 설명
- 요청된 작업 범위를 지키고 과거 Goal·다음 실험을 자동 시작하지 않는 규칙
- 실패·미실행 검증과 실제 성공을 구분하는 완료 기준
- 기존 사용자 승인 범위를 존중하고 승인되지 않은 push·merge·배포 등을 자동 수행하지 않는 규칙
- 사용자가 직접 구현하겠다고 하면 설명·힌트 중심으로 전환하는 규칙
- ML smoke/full 구분, 데이터 누수 방지, 원본·canonical 산출물 보존
- 실행 기록의 미검증 범위와 rollback 정보

## 3. 수정 후 각 파일의 책임

`migration-harness/`만 기존 `docs/archive/` 아래로 이동한다. 다른 하네스 경로는 유지하며 별도의 정책 형식이나 호환용 실행 폴더는 만들지 않는다.

| 위치 | 남길 책임 | 덜어낼 내용 또는 이동 방향 |
| --- | --- | --- |
| `AGENTS.md` | 공통 경계, 변경·검증 원칙, 현재 사용하는 AI 지침 선택, 직접 구현 모드 전환 | migration 활성화·읽기 순서·다음 Goal 진행 규칙 제거. 당시 Goal을 전제로 한 예외와 현재 상태 설명도 갱신한다. |
| `ai-harness/README.md` | 작업 모드 선택과 실행 지침의 입구 | 반복 조합 예시와 낡은 실행 설명 정리 |
| `ai-harness/tasks/*.md` | 해당 작업의 입력·진행 방식·확인 기준 | 루트 규칙 재서술을 줄이고 작업별 차이만 유지 |
| `docs/archive/migration/README.md` | 보관한 문서의 의미, 종료 상태, 현재 문서로 가는 링크 | 상단에 과거 기록이며 현재 실행 지침이 아님을 명시. 기존 설명은 당시 구성으로 보존 |
| `docs/archive/migration/goals/`, `runs/` | 당시 목적·계약·실행 결과·위험과 rollback 근거 | 본문 사실 보존. 이동에 따른 탐색용 상대 링크만 필요한 만큼 수정 |
| `docs/archive/migration/`의 나머지 문서 | 당시 roadmap·제약·workflow·프롬프트 | 실행 가능한 현재 지침으로 유지보수하지 않음. 실행 프롬프트에는 과거 템플릿임을 표시 |
| 현재 README·PLAN·운영·품질 문서 | 현재 구조·운영·검증 기준 및 과거 증거로의 연결 | 활성 migration 안내 제거, archive 링크와 현재 기준 링크 구분 |
| `ai-harness/ml-experiments/` | MODE별 절차와 실험 계약 | 현재 MODE와 무관한 설명의 필수 읽기 축소. 실험별 경로·계약은 유지 |

현재 상태와 다음 작업은 기존 `PLAN.md`, 완료 이력은 `change-log.md`의 역할을 유지한다. 하네스에 현재 브랜치·HEAD·테스트 수를 중복 저장하지 않는다.

## 4. 단계별 실행 계획

### 1단계 — 종료된 migration 기록 보관과 활성 참조 정리

대상: `migration-harness/` 전체, `AGENTS.md`, README·PLAN, migration을 참조하는 운영·품질·이력 문서, 본 계획의 근거 링크.

1. 파일 목록과 내용을 기준선으로 기록하고 저장소 전체에서 링크·문자열 참조·테스트 의존성을 확인한다. 현재 조사한 scripts/test/python_tests/.github/package.json에서는 migration 경로 의존성이 발견되지 않았으나 이동 직전에 다시 확인한다.
2. migration에만 적혀 있으면서 현재도 필요한 조건을 확인한다. 기존 아키텍처·운영·품질 문서나 검증 스크립트에 이미 있으면 그 위치를 참조하고, 없으면 필요한 조건만 기존 적합한 문서에 옮긴다.
3. 폴더를 `docs/archive/migration/`으로 이동하되 goals/runs/prompts 등 내부 구조를 유지한다. 과거 커밋·날짜·결과·checksum과 보류 상태를 보존한다.
4. archive README와 실행 프롬프트에 종료된 작업의 기록이며 새 작업의 실행 권한·현재 명세가 아님을 표시한다. 새 migration 요구가 생기면 당시 계획을 참고하되 현재 코드 기준으로 새 범위를 정한다.
5. 같은 변경에서 `AGENTS.md`의 migration 활성화 지침을 제거하고 README의 로드맵 링크를 과거 마이그레이션 기록으로 바꾼다. 이전 폴더에 중복 파일·symlink·실행 안내를 남기지 않는다.
6. 외부 문서에서 archive로 들어오는 링크와 이동한 문서에서 저장소로 나가는 상대 링크를 모두 확인한다. 같은 하위 구조 안의 링크는 불필요하게 변경하지 않는다.
7. 명령 예시·Git 경로·실행 로그에 포함된 당시 문자열은 역사적 값으로 구분해 보존한다. 전역 치환으로 과거 기록을 현재 경로에서 실행한 것처럼 바꾸지 않는다.
8. DB blueprint의 “production 미활성·JSONL 현재 경로” 설명은 PLAN의 배포 완료 기록과 시점이 다르다. 해당 범위를 당시 상태로 표시하고 최신 확인 근거에 연결한다. 실제 운영 환경을 이번 문서 작업에서 새로 점검했다고 주장하지 않는다.
9. production runbook의 Goal 9D release gate 참조는 현재 package scripts·CI와 대조해 직접 실행할 검증 기준으로 정리하고, 당시 Goal은 근거 링크로 남긴다.

완료 기준: 루트의 migration 실행 경로가 제거되고 모든 기록에 계속 접근할 수 있다. 현재 운영 검증은 archive를 실행 지침으로 읽지 않아도 찾을 수 있으며 보류 Goal은 자동 재개되지 않는다.

### 2단계 — 루트 지침과 작업 선택 정리

대상: `AGENTS.md`, `ai-harness/README.md`, 필요한 `tasks/*.md`, 기존 teaching guide.

1. 현재 규칙을 공통 경계, 작업 방식, 설명 스타일, 과거 배경으로 구분한다.
2. 공통 경계는 루트에 한 번만 남긴다. 세부 설명은 기존 작업 문서와 guide로 모은다.
3. archive는 과거 설계·작업 이유를 묻는 경우에만 필요한 문서를 읽는다. ML 하네스는 해당 실험 요청에서만 선택한다.
4. 직접 구현 의사 표현과 구현 요청을 구분한다. 이미 허용된 작업을 반복해서 승인받는 문구는 만들지 않는다.
5. AI README의 검증 설명과 실제 파일 확장자를 현재 코드에 맞춘다.

완료 기준: 단순 설명·버그 분석·구현 요청에서 필요한 작업 문서를 고를 수 있고, 공통 안전·학습 규칙이 빠지지 않는다. `AGENTS.md` 약 120~160줄을 편집 목표로 삼되 중요한 계약을 줄 수에 맞춰 삭제하지 않는다.

### 3단계 — ML 진입 지침과 기존 검증 연결 정리

대상: ML README·workflow·verification, 관련 AI 작업 지침.

1. `implement-smoke`, `run-full`, `analyze-result`, `freeze-audit`의 공통 계약과 MODE별 절차를 구분한다.
2. teaching guide는 학습 중심 요청에 선택적으로 적용한다. 구현 작업에 필요한 설명은 유지한다.
3. 오래 유지하기 어려운 모델명·추론 수준 추천은 필수 실행 계약에서 제외한다. 모델 비교 조사는 이번 범위에서 수행하지 않는다.
4. 기본 검증은 기존 `scripts/verify.sh`, ML 검증은 기존 `scripts/verify-ml.sh`와 실험별 검증을 재사용한다. 같은 실행 결과를 불필요하게 중복 실행하지 않는다.
5. 문서에 적힌 승인·MODE와 실제 실행 권한을 구분한다. MODE나 환경변수를 에이전트가 설정했다고 full 실행 승인이 생긴다고 해석하지 않는다.
6. 기존 실험 명세, Notebook, 테스트, 데이터 경로는 변경하지 않는다. 이 영역의 실제 변경이 필요하면 본 문서 정리와 분리한다.

완료 기준: report 해석 요청이 재학습이나 full 실행으로 이어지지 않고, smoke 완료를 모델 성능 검증이나 production 승인으로 보고하지 않는다.

### 4단계 — 문서 검증과 대표 요청 점검

1. 변경된 Markdown의 상대 링크·파일 경로·코드 블록 짝·공백 오류를 확인한다.
2. `rg`로 하네스 참조를 다시 검색한다. migration 탐색 링크는 archive로 연결되고 Python 테스트가 읽는 ML 경로는 유지되는지 확인한다. 남은 옛 migration 문자열은 당시 명령·이력인지 분류한다.
3. 아래 요청을 기준으로 수정 전후에 읽을 문서와 행동을 비교한다. 실제 migration·full 실험·Git 쓰기 작업은 수행하지 않는 문서 검토다.
4. 적용 중인 안전·학습·완료 조건이 축소 과정에서 사라지지 않았는지 확인한다.
5. 이동 전후 기록의 파일 수와 내용을 비교하고 허용한 안내·링크 수정 외 손실이 없는지 확인한다. 활성 루트 지침의 전후 분량은 기록하되 archive 이동량을 매 요청의 토큰 절감으로 계산하지 않는다.

| 대표 요청·상황 | 기대 결과 |
| --- | --- |
| “이 함수의 흐름을 설명해줘” | 필요한 코드와 설명 지침을 읽고 migration archive·ML 절차는 활성화하지 않는다. |
| “내가 직접 구현해볼게” | 코드를 대신 수정하지 않고 개념·힌트·검증 기준을 제공한다. |

| “새로운 기술 전환을 진행하고 싶어” | 현재 요구·코드에서 새 범위를 정하고 보류된 과거 Goal을 자동 재개하지 않는다. |
| 선행조건 불충족 또는 관련 사용자 변경 발견 | 기존 변경을 보존하고 해결 가능한 환경 문제와 사용자 결정이 필요한 충돌을 구분한다. |
| “ML 실험을 implement-smoke로 진행해줘” | 작은 smoke까지 수행하는 절차를 선택하고 full 명령만 제공한다. |
| “기존 full report를 해석해줘” | report의 입력·계약·검증 증거를 확인하고 재학습을 시작하지 않는다. |
| 필수 검증 실패·미실행 | 완료로 보고하지 않고 실패와 미검증 범위를 드러낸다. |
| “문서만 정리해줘” | 문서 검증을 수행하고 불필요한 게임 전체 검증은 생략 사유와 함께 보고한다. |

위 비교는 지침의 일관성 검토다. 실제 에이전트의 준수율을 측정한 평가가 아니다. 이후 실제 작업에서 범위 이탈·검증 누락·과도한 재질문이 있었는지 관찰해 필요한 부분만 보완한다.

## 5. 스크립트와 훅의 후속 판단

이번 계획의 기본 실행 범위는 위 1~4단계다. 훅의 존재 자체를 완료 조건으로 삼지 않는다.

- 종료된 migration의 Node·Git ancestry 절차만을 위한 preflight 스크립트는 만들지 않는다. 현재 개발에서 반복 누락되는 검사가 확인되면 기존 스크립트에서 해결할 수 있는지 먼저 본다.
- 훅이 필요해지면 먼저 방지할 행동 하나, 적용 도구, 통과·차단·잘못된 입력·실행 오류의 기대 결과를 정한다. 단순 명령 문자열 검사를 완전한 접근 통제로 취급하지 않는다.
- 매 도구 호출 또는 매 응답 종료마다 전체 검증을 실행하는 방식은 도입하지 않는다.
- 향후 스크립트·테스트·실행 설정을 실제로 변경하면 작은 동작 테스트와 `bash scripts/verify.sh`를 수행한다. 훅을 추가한다면 사용 환경에서의 실제 호출 확인도 별도로 필요하다.

## 6. 검증 범위와 되돌리기

- 본 계획 작성: 신규 문서의 링크·코드 블록·공백 및 변경 범위를 확인한다. 런타임 테스트는 실행하지 않는다.
- 1~4단계 문서 수정: 문서 검증과 대표 요청 점검을 수행한다. 테스트가 읽는 실험 문서나 계약을 실제로 수정하게 되면 해당 Python 계약 테스트도 수행한다.
- 단계별 변경을 독립적으로 검토할 수 있게 유지한다. 커밋 여부는 실행 시 사용자 지시를 따른다.
- 되돌릴 때 archive 경로 이동과 그에 따른 링크·활성 지침 변경을 함께 역으로 적용한다. 사용자 기존 변경, 학습 문서 이동, 데이터와 Git 이력은 건드리지 않는다.
- 공통 문서에서 조건을 제거할 때는 같은 변경 안에서 새 기준 위치와 참조를 먼저 확보한다.

## 7. 최종 완료 조건

- 종료된 migration 명세·실행 증거와 현재 ML 실험 계약이 보존된다.
- 공통 규칙의 기준 위치가 분명하고 읽기 지침이 서로 모순되지 않는다.
- 현재 실행 지침이 종료된 migration 절차에 의존하지 않고 일반 요청에서 archive·무관한 ML 문서를 필수로 읽지 않는다.
- 문서의 검증 명령과 실제 스크립트가 일치한다.
- migration 링크가 archive로 연결되고 ML 테스트의 기존 문서 경로 의존성은 유지된다.
- 문서상 절차, 실제 자동 검사, 사람이 판단할 부분을 구분한다.
- 변경 내용, 확인 결과, 미검증 범위와 후속 자동화 필요 여부를 보고한다.

대표 요청의 문서 검토 결과:

- 설명·직접 구현: 필요한 작업 모드만 선택하고 직접 구현 요청에는 코드 수정을 중단한다.

- ML smoke·기존 full report 해석: smoke에서 full 실행으로 넘어가지 않으며 report 해석이 데이터 편입·재학습을 시작하지 않는다.

- 대표 요청 점검은 지침 일관성 검토이며 실제 에이전트 실행 평가나 토큰 절감 측정이 아니다.
