## CI 구현

기존 세 job 이름과 책임은 바꾸지 않았다. `Fast gate` 성공 뒤 `Chromium PVP and PVE`, `Production container smoke`, 신규 `PostgreSQL event storage`가 병렬로 실행된다. workflow 권한은 계속 `contents: read`뿐이다.

신규 job은 clean checkout, `.nvmrc` Node, `npm ci --ignore-scripts`, service health, 기존 실제 DB integration suite와 production-like Docker gate를 순서대로 실행한다. setup-node cache를 설정하지 않아 cache miss에도 독립적이다. job-local test credential만 쓰고 URL/password를 mask하며 DB dump, JSONL, Playwright trace와 실패 artifact를 업로드하지 않는다. workflow retry, `continue-on-error`와 고정 장기 sleep은 추가하지 않았다.

GitHub Actions service는 job-local loopback non-TLS라 기존 private-CA TLS subtest 한 건만 명시적으로 skip한다. 나머지 migration, schema-role, repository, importer, runtime과 source-less artifact 7건은 같은 PostgreSQL service에서 실행한다. private CA 성공, untrusted CA와 hostname mismatch 실패는 local isolated PostgreSQL fixture의 8/8 suite에서 계속 검증한다.

## Production-like Docker 검증

`npm run test:docker:postgres`는 Goal 전용 label·random suffix의 network, PostgreSQL volume/container, application image/container와 임시 directory만 만든다. 종료 trap은 자신이 만든 resource만 정리한다.

- migration/runtime/maintenance role 분리와 runtime `DELETE` 거부
- non-loopback private CA와 hostname 검증 TLS
- `GAME_EVENT_STORAGE=postgres` 단일 sink, JSONL mount 없음, JSONL 생성·append `0`
- PVP/PVE start, placement, over event 저장: `26` row, privacy violation `0`, duplicate event ID `0`
- application restart 전후 row count/hash 동일
- synthetic backup/restore 전후 row count/hash 동일
- PostgreSQL pause 중 PVE gameplay 통과, redacted write failure `attempts=3`, credential/payload log `0`
- pool `4`, in-flight `16`, ticker `100ms` 상수와 shutdown 뒤 runtime pool connection `0`
- SIGTERM 두 번 exit `0`, 최종 측정 `219ms`, `222ms`

첫 production smoke는 test SQL에서 `COALESCE`를 잘못 schema-qualified해 PVP/PVE 뒤 실패했다. SQL built-in 표기로 수정하고 전체 smoke를 재실행했다. 최종 리뷰에서 image credential/JSONL mount assertion과 retention delete의 byte 상한을 추가했으며, 첫 재현에서 `DELETE ... ## 보안·운영 결과

- workflow credential은 job-local test 값이며 production secret을 사용하지 않는다.
- URL, password, raw payload가 application log에 없음을 실패 경로에서 검사한다.
- runtime role은 DDL/UPDATE/DELETE/TRUNCATE 권한이 없고 retention은 maintenance role만 수행한다.
- TLS는 non-loopback에서 CA와 hostname 검증을 요구한다.
- raw retention 목표는 90일, quota warning은 70%, emergency는 85%다.
- 자동 retention은 없으며 실제 사용자 row 삭제 승인자는 프로젝트 운영자인 사용자다.
- DB failure는 승인된 best-effort 수집 경계다. 최대 3회·2.7초 뒤 event가 유실될 수 있지만 gameplay는 계속하고 불완전 game은 learning export에서 제외한다.
- provider와 one/two-VM 배치는 결정하지 않았다. [운영 runbook](../../docs/postgres-production-runbook.md)은 provider-neutral 절차만 기록한다.

## 자체 리뷰

- P0: 없음.
- P1: 없음. service authentication과 production smoke SQL의 구현 중 실패는 위와 같이 원인을 고치고 전체 경로를 재실행했다.
- P2 해결: application image의 DB credential env 부재와 application container의 JSONL mount 부재를 explicit assertion으로 고정했다. retention delete도 dry-run과 같은 row/byte 상한을 parameter로 다시 적용하며 실제 PostgreSQL의 qualified `RETURNING`까지 검증했다.
- P3: 없음. 새 dependency, retry wrapper, CI framework와 범용 abstraction을 추가하지 않았다.

## 남은 gate와 위험

- branch가 push되지 않아 같은 SHA의 hosted 네 job과 cache-miss clean run은 아직 실행하지 않았다. run URL, hosted SHA, 시간과 cache 상태는 승인 후 이 기록에 추가한다.
- production provider TLS, managed backup/restore, quota/비용과 실제 latency는 provider가 정해진 뒤 별도 환경에서 검증해야 한다.
- production DB/secret, 실제 사용자 JSONL과 row에는 접근하지 않았다.
- PostgreSQL runtime은 구현돼 있지만 production에서 활성화하지 않았다. JSONL은 계속 기본 sink다.
- strict lossless가 필요하면 Goal 9D를 production enable 근거로 쓰지 않고 durable outbox를 별도 설계한다.

## Rollback

1. 아직 hosted/main 통합 전이므로 문서 commit, production-boundary test commit, CI commit 순서로 역순 revert한다.
2. production enable은 없으므로 runtime data rollback은 없다.
3. 향후 활성화 뒤 rollback은 이전 image와 명시적 `GAME_EVENT_STORAGE=jsonl` 및 보존 JSONL volume/path를 복구한다.
4. PostgreSQL table/row와 기존 JSONL을 삭제하지 않는다. down migration과 automatic retention을 실행하지 않는다.
5. test가 만든 synthetic row/database/container/volume/network와 임시 dump만 test 종료 시 정리한다.

hosted CI 실행은 별도 승인 뒤에만 진행한다. 네 job이 모두 green이고 cache-miss clean run이 확인되기 전에는 Goal 9D를 complete 처리하지 않는다.
